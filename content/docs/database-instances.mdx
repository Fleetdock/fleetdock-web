An **instance** is a database server process that Fleetdock manages — the dashboard calls it a
**database server**. Fleetdock supports **MariaDB, MySQL, and PostgreSQL**. This page covers
adding database servers, their lifecycle, and connecting to them.

## Managed vs external instances

- **Managed** instances run on your nodes. They are either **provisioned** by Fleetdock (a
  database Docker container it launches) or **registered** (an existing database on the
  node). Operations run through that node's agent against `127.0.0.1`.
- **External** instances are databases you already host elsewhere. The control plane
  connects to them directly, optionally through an SSH tunnel.

Whichever kind, Fleetdock **discovers the databases** on it automatically once it has an admin
login: right after you add it, then every minute.

## Adding a database server

Open **Databases → Connect database server**, or **Add database server** on a server's page
(which preselects that server). Choose one of three options:

| Option | What it does |
| --- | --- |
| **Create a new one** | Fleetdock starts a fresh database server in Docker on one of your connected servers (provisioned). |
| **Use one on my server** | A database server already runs on one of your connected servers; Fleetdock manages it through the agent (registered). |
| **Connect to one anywhere** | Any database server Fleetdock can reach over the network — hosted, cloud, or on another machine (external). |

### Fields

- **On which server?** — the connected server, for the first two options.
- **Engine** — PostgreSQL (the default), MySQL, or MariaDB.
- **Version** — for a new server, the image version to run. The dashboard offers PostgreSQL
  18, 17 (the default), 16, 15 and 14; MySQL 8.4; and MariaDB 11.8, 11.4 (the default), 10.11
  and 10.6. For an existing server, the version running there.
- **Name** — how it appears in Fleetdock, for example `production` or `analytics`.
- **Port** — for a new server, the port it listens on, on its host (`5432` for PostgreSQL,
  `3306` for MySQL and MariaDB by default); pick a free one. Otherwise, the port it already
  listens on.
- **Host** and an optional **SSH tunnel** — external servers only. On the same computer as
  Fleetdock, use `host.docker.internal`; `localhost` would mean Fleetdock's own container.
- **Admin user** and **Password** — existing servers only: an account allowed to create
  databases and users. Fleetdock needs it to find databases, take backups and show
  monitoring. You can add it later with **Add login** on the database server's page.
- **Encryption** — how Fleetdock secures its connection: use encryption when available (the
  default), always encrypt, always encrypt and verify the certificate, or never encrypt.
- **Data browsing connects as** — the admin login, a dedicated login you create, or
  Fleetdock-managed roles per database. See [Data browser](/docs/data-browser).
- **Include pgvector** — new PostgreSQL servers only (14 or newer in the dashboard): runs the
  official `pgvector/pgvector` image for that major version instead of `postgres`, so
  `CREATE EXTENSION vector` works. It needs a 0.12 agent. See
  [Extensions](/docs/postgresql#extensions).

For a new server, Fleetdock generates a strong admin password and keeps it encrypted, and
starts it with a named Docker data volume and the published port. Follow its progress with
**Follow progress**; it usually takes under a minute.

<Callout type="info">
  Creating a new database server requires Docker on the node; the agent installer installs it
  automatically. MySQL 8.0, past its end of life, is no longer offered for new servers, but
  existing MySQL 8.0 servers keep working.
</Callout>

## Status lifecycle

From a database server's page you can:

- **Check now** — check the connection and look for new databases immediately, instead of
  waiting for the next minute's check. The page shows when it was last checked and its health.
- **Start**, **Restart** and **Stop** a server Fleetdock created (Restart and Stop are in the
  **⋯** menu).
- **Edit** its name, connection settings and login (**Add login** when it has none).
- See its **Databases**, and with a login, **Monitoring** and **Database users** with their
  grants.
- **Remove…** it from Fleetdock.

## Restarting, stopping, and removing

Start, stop, and restart act on the container of a server Fleetdock created. Stopping
disconnects every application until you start it again; no data is deleted. Removing a server
Fleetdock created stops and removes its container and, if you tick the option, deletes its data
volume; otherwise the volume is kept and can be reattached later. Removing any other database
server only removes it from Fleetdock — the server itself is not touched.

<Callout type="error">
  Deleting the data volume of a removed database server permanently destroys all of its
  databases. Back up first.
</Callout>

## Inspecting logs

Container-level logs are available on the node with standard Docker tooling:

```bash
docker logs <container-name>
```

Task history (create, drop, backup, restore, move) is on the **Activity** page, and every change
made through Fleetdock is in **Activity → Audit log**.

## Connecting from external applications

How you connect depends on where your application runs.

### Private network (recommended for internal apps)

Provisioned instances publish a port on the server. Connect with the client for your engine
using the server's internal address and the published port:

<Tabs items={["MariaDB / MySQL", "PostgreSQL"]}>

<Tab value="MariaDB / MySQL">

```bash
mariadb -h <server-address> -P <published-port> -u <user> -p
```

</Tab>

<Tab value="PostgreSQL">

```bash
psql "postgresql://<user>@<server-address>:<published-port>/<database>"
```

</Tab>

</Tabs>

<Callout type="warn">
  The instance port must be reachable from wherever your application connects — and, for
  live administration, from the control plane. Keep it on a private network where possible.
  See [Networking](/docs/networking).
</Callout>

### Public access via Fleetdock Gateway

For applications **outside** your private network, enable **public access** on the database
page (**Connection** tab). Fleetdock assigns a stable gateway endpoint
(`gateway.example.com:<port>`) and routes traffic through HAProxy with CIDR enforcement.

<Callout type="info">
  Public access is **disabled by default**. Do not expose database ports directly to the
  internet as your primary pattern — use the gateway with application credentials and CIDR
  allowlists. See [External database access](/docs/external-access).
</Callout>

Use **application credentials** (not instance root credentials) for external apps. The
connection URL is shown once on create or rotate.

## Databases on an instance

Within an instance you create logical **databases**. When admin credentials exist, creating
a database physically creates it via an operation; otherwise it is registered as
metadata-only. Databases can be locked, unlocked, and soft-deleted with a seven-day
recovery window.
